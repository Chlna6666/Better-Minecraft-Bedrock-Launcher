# bedrock-world 0.7 API migration

`bedrock-world` 0.7 is a breaking release that makes the crate a dedicated **Minecraft Bedrock world-semantics layer** on top of `bedrock-leveldb`.

The public API is organised by Bedrock data domains. Generic software-layer namespaces such as `model`, `codec`, `storage`, `migration`, and `upgrade` are not public compatibility surfaces.

## Domain API

```rust
use bedrock_world::{
    block::{BlockState, BlockStateMigrationGraph},
    chunk::{ChunkPos, Dimension, HistoricalChunkMigrationOptions},
    database::WorldStorage,
    entity::ActorMigrationAction,
    integrity::{CompatibilityLevel, WritePolicy},
    nbt::NbtTag,
    query::query_chunk_detail_blocking,
    world::{BedrockWorld, OpenOptions, WorldMigrationPlan},
};
```

### `block`

Block positions, `BlockState`, palettes, block entities, canonical semantic identity, and versioned BlockState migration rules/graphs.

### `chunk`

Chunk coordinates and keys, `LegacyTerrain`, SubChunk v0-v9 parsing, historical numeric-block resolution, and explicit conversion to a caller-selected authoritative paletted target.

Historical conversion is staged:

```text
LegacyTerrain / SubChunk v0-v7 / old paletted state
        -> historical decode
        -> versioned BlockState migration
        -> compact canonical palette + indices
        -> authoritative target-palette validation
        -> target paletted SubChunk
```

SubChunk versions unknown to the library are preservation-only and block destructive migration.

### `biome`

`Data2D`, `Data2DLegacy`, `Data3D`, height maps, legacy saved biome colours, and explicit 2D-to-3D promotion.

### `entity`

Legacy inline `Entity` records, modern `digp`/`actorprefix` records, actor identities, and atomic inline-to-digest migration.

### `player`

Player records/items and migration of historical embedded `level.dat.Player` data into `~local_player` storage.

### `level`

`level.dat` parsing, atomic writes, map-owned seed preservation, and guarded metadata migration.

### `database`

Bedrock world-record storage abstractions and the `bedrock-leveldb` adapter. Minecraft chunk/entity/biome semantics do not belong in `bedrock-leveldb`.

### `world`

World lifecycle, discovery, scans, transactions, mixed-version migration planning, and pre-LevelDB `chunks.dat` import into the normal world-storage abstraction.

### `integrity`

Read-only compatibility/integrity scanning. Mixed-format worlds are classified per record/chunk instead of trusting one global storage version.

### `editor` and `query`

Typed policy-guarded mutations and read-only high-level queries.

## Multi-version compatibility policy

World compatibility is classified as:

- `Exact`
- `ReadCompatible`
- `MigrationRequired`
- `UnsupportedFuture`
- `Corrupt`

Write policy is explicit:

- `Preserve`: write only when the existing physical representation can be retained safely.
- `Migrate`: require a verified migration path and authoritative target data.
- `Refuse`: read-only behaviour.

## Unknown data preservation

Unknown NBT fields and unsupported future records are retained whenever possible. Unknown data is never interpreted as safe to delete or downgrade.

## Dependency direction

```text
bedrock-leveldb  (Mojang LevelDB bytes/storage mechanics)
      ↓
bedrock-world    (Minecraft Bedrock world semantics)
      ↓
renderers / editors / servers
```

`bedrock-world` may depend on `bedrock-leveldb`. `bedrock-leveldb` must never depend on Minecraft world semantics.
