# bedrock-world 0.7 API migration

`bedrock-world` 0.7 is a breaking release that makes the crate a dedicated **Minecraft Bedrock world-semantics layer** on top of `bedrock-leveldb`.

The old crate-root type/function facade is no longer the supported API. Consumers use responsibility modules directly.

## Public API layers

```rust
use bedrock_world::{
    audit::{CompatibilityLevel, WritePolicy},
    codec::NbtTag,
    edit::block_edit,
    migration::BlockStateMigrationGraph,
    model::{BlockState, ChunkPos, Dimension},
    query::query_chunk_detail_blocking,
    storage::WorldStorage,
    world::{BedrockWorld, OpenOptions},
};
```

Do not use the former flat API:

```rust,ignore
use bedrock_world::{BedrockWorld, ChunkPos, NbtTag, OpenOptions};
```

## Responsibility boundaries

### `model`

Semantic world data only:

- coordinates/dimensions,
- chunk records,
- BlockState/palette models,
- players/items,
- actors/entities,
- block entities,
- biomes/height maps,
- maps/villages/global records.

### `codec`

Bytes/NBT to semantic model and back. Codecs do not decide migration or write policy.

### `migration`

Historical format conversion:

- BlockState version migration graph,
- legacy numeric `id:data` resolver,
- LegacyTerrain and old SubChunk migration,
- `Data2D` to `Data3D`,
- legacy inline `Entity` to `digp`/`actorprefix`,
- old `level.dat`/player migration,
- pre-LevelDB `chunks.dat` import.

Migration is explicit. Unknown future formats are preserved/read-only rather than guessed.

### `edit`

Typed mutations guarded by compatibility/write policy. Normal edits must not silently rewrite unrelated chunk-generation state such as `FinalizedState`.

### `audit`

Read-only compatibility and integrity scanning. Mixed-format worlds are detected per record/chunk instead of trusting one global storage version.

### `query`

Read-only high-level map/world queries.

### `storage`

World-record storage abstraction and the `bedrock-leveldb` adapter. Storage does not own migration policy.

### `world`

High-level world lifecycle, chunk loading, scans and transactions.

## Multi-version compatibility policy

World compatibility is classified as:

- `Exact`
- `ReadCompatible`
- `MigrationRequired`
- `UnsupportedFuture`
- `Corrupt`

Write policy is explicit:

- `Preserve`: write only when the existing format can be preserved safely.
- `Migrate`: require a verified migration path and authoritative target data.
- `Refuse`: read-only behavior.

## Seed ownership

For an existing world, `level.dat` owns `RandomSeed`.

- An existing valid seed is never overwritten by application configuration.
- A missing seed may be initialized explicitly once.
- A malformed/unreadable existing seed is an error, not a reason to fall back to another seed.

This prevents old and newly generated chunks from being created with different seeds.

## Unknown data preservation

Unknown NBT fields and unsupported future records must be retained whenever possible. "Unknown" never means "safe to delete".

## Dependency direction

```text
bedrock-leveldb
      ↓
bedrock-world
      ↓
renderers / editors / servers
```

`bedrock-world` may depend on `bedrock-leveldb`. `bedrock-leveldb` must never depend on Minecraft world semantics.
