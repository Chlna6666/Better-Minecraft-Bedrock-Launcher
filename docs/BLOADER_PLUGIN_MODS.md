# BMCBL 插件虚拟 Mod 与 BLoader 的交接协议

插件包可以携带 Minecraft 原生模组。BMCBL 管理插件、载荷摘要和每个游戏版本的授权。BLoader 接受本次启动的模组计划并管理游戏进程内的加载阶段。BMCBL 当前实现包注册和版本开关；下述加载计划与会话协议是 BLoader 端的实现契约。

## 包清单与授权

插件的 Cargo 元数据使用如下声明，打包器把它写入 `plugin.toml` 的 `[[game_mods]]`，并把文件装入同一个 `.bmcblx`。

```toml
[[package.metadata.bmcbl-plugin.game_mods]]
id = "example-mod"
name = "Example Mod"
path = "game-mods/example.dll"
platform = "windows-x86_64"
phase = "ready"
game_versions = ["1.21.120", "26.10"]
```

- `id` 在所属插件内唯一。载荷路径是包内 `game-mods/` 下的相对路径，文件为最多 32 MiB 的 x64 PE DLL。
- `game_versions` 是点分版本前缀。匹配须在组件边界结束，例如 `26.10` 可以匹配 `26.10.2`。
- `preload` 对应 BLoader 自有的 `mod-preload` 阶段，`ready` 对应 `mod-native`。LeviLamina 和 PreLoader 继续处理各自的模组类型。
- 管理页的「授权并启用」将游戏版本、`<plugin-id>/<mod-id>` 和当前载荷 SHA-256 绑定。插件关闭、卸载、版本不匹配、载荷摘要变化或版本禁用 Mod 加载时，该授权不进入启动计划。
- BMCBL 以插件安装位置管理文件，各版本共享该文件。启停状态存放在 BMCBL 自己的状态目录，游戏实例的模组目录无需增加文件。

## 启动计划协商

1. BMCBL 为用户发起的当前游戏启动创建一次性会话，绑定游戏版本、启动实例和 BLoader 连接。Windows 使用限定到当前用户和本次实例的本地管道或等效继承句柄。Linux Wine/Proton 链路需要提供同样的访问约束，并由宿主负责路径转换。
2. BLoader 先发送 `hello`，声明协议主版本、可用阶段和最大消息字节数。BMCBL 对端点身份和本次启动会话进行核对。双方均支持协议主版本 `1` 并通过验证后才接受启动计划。认证材料只走一次性通道，过期后销毁。
3. BMCBL 发送本次启动允许的 `module-id`、`sha256`、`platform`、`phase` 和宿主管理的载荷引用。BLoader 检查平台及阶段，复核实际打开的文件与计划摘要相符，并在验证通过的同一份载荷上继续加载。载荷应以只读方式交接，避免路径被调换后验证和加载落在不同文件上。
4. BLoader 每个阶段按模组 ID 返回结果。状态至少区分已接收、已加载、不兼容、校验失败与加载失败。协议不支持或协商失败时，本次启动跳过虚拟模组。游戏原有启动结果独立报告。

## 运行中消息

- 帧使用长度前缀，载荷上限由协商双方取较小值，初始上限 64 KiB。请求包括会话 ID、模组 ID、请求 ID、方法及载荷。响应携带原请求 ID 和结果。宿主验证消息发出者和模组归属，再转发给当前有效的插件实例。
- 每个模组维护有限的并发与等待队列。请求超时、连接断开、游戏退出、插件卸载或版本禁用时，撤销转发权限并完成等待中的请求。已加载的原生模组随游戏进程结束。
- 插件输入限于自己的模组 ID 和业务消息。进程、路径、加载阶段及会话归属由 BMCBL 决定。账号功能调用启动器原有的授权流程，令牌和凭证留在既有认证通道内。

联调至少覆盖两个版本共享同一载荷、独立启停、摘要变化后重新授权、旧协议协商失败、错误会话、超长帧、加载状态和请求响应往返。
